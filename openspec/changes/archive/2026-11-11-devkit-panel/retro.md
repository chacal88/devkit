## Retro: devkit-panel

1. Went wrong: the pack shipped (four phases, 59 tests, four approved reviews, PR #18 squash-merged at 8/8), and the ship cost more than the pack. (a) The rebase onto main after `conduct-one-change` merged could not use `release-rebase.mjs`: `docs/openspec-flow.md` conflicted, because its CI pin follows every devkit-openspec release while the file is not in `RELEASE_FILE` (and the panel section lives in the same file), so the script exits 2 and the rebase was done by hand (design D14). The conduct-sessions retro (item 8, left as a followup) and the conduct-one-change retro (item 9) had already met the same collision from the other side; it bit a third time. (b) The mod gates: `claude plugin test` exists only in the desktop app's bundled Claude Code, whose mods rollout switch lapses about two minutes after a `-p` warm-up; the readiness review spent three of its four rounds getting the four gate lines into the shape the flow reads (the binary by absolute path, one backticked `&&` command per gate, `plugin test` before the six-minute guard suite), and nothing in `CONTRIBUTING.md` or `docs/conventions.md` says how a mod pack is tested or how a gate line is parsed. (c) `scripts/check.py#check_language` scans every `*.md`, review verdicts included: a reviewer quoting two pt-BR strings of the pane made CI red at 2da5893 (code-quality round-3 nit), fixed by rewording. (d) The conducting session was started in another repository's folder, so the devkit-core agent types were not loaded: every role ran as a general-purpose subagent following the agent file, and the hooks did not enforce the one-writer rule (recorded in requirements, readiness, all four reviews and evidence; the adr-reviewer carried it as an open nit). (e) The sibling change landed `/conduct <id>` on main while this change was in review; after the rebase a `create` row's bare `/conduct` no longer reached the schema question and the probe on the first row read as `no` for the whole session: two `[important]` findings in review round 3 (architecture reviewer), fixed in 91081b2, one round later than a re-read after the rebase would have cost. (f) The `--change` probe spends a full `conduct-check` run (with its `gh` calls) once per session to learn whether the installed checker accepts the option, because the checker exposes no list of accepted options (architecture nit, carried since round 2). (g) Phase 4, the live check, is run by the conducting session with the owner at the keyboard, which the flow does not model: `tasks.md` carries a paragraph telling a dispatched child to fail at once, and task 4.1 was `not offered` by the app. Smaller: AC-13's child-session half had nothing to draw (no phase session of round 5 exists), so `evidence.md` records it as `no proof`.
2. Better next time: fix the pin collision in the tooling instead of recording it a third time (proposal 1); write the mod-gate recipe once, where a plan author reads it, so the next mod plan passes readiness in one round (proposal 2); let `check_language` skip backticked text, since a quoted string is not prose (proposal 3); start the conducting session on the project's folder, or know what the deviation costs and where to record it (proposal 4); after a rebase onto a base that merged a sibling, re-read what the change consumes from that sibling before pushing the rebased head (proposal 5); give the checker a list of its options and the flow an owner-run phase, each as a change of its own (rows 6 and 7).
3. Remember: a collision two retros already filed as a followup is not a followup any more; it is the next change.

### `CONTRIBUTING.md` (doc-gap)
Under "Testing a pack locally", after the `claude plugin update` sentence: how a mod pack is tested and how a gate line is read, the two things the devkit-panel plan learned over three readiness rounds.
- before: (none: the section ends with "A session runs the pack installed at project scope, not the working tree: ... or load the tree with `--plugin-dir` as above.")
+ after: a new paragraph: "**Testing a mod pack.** A pack of hooks modules (`plugins/panel`) is tested with `claude plugin test <dir>`, which only the desktop app's bundled Claude Code has: `"$HOME/Library/Application Support/Claude/claude-code/<version>/<hash>/claude.app/Contents/MacOS/claude"` (the npm `claude` has no `plugin test`, and its `plugin validate` rejects a `modules` hooks.json). Before a run, `<that binary> plugin test --help` must print `Run a mod's tests`; when it prints the rollout-switch refusal instead (exit 0 as well), run `<that binary> -p "ok" --max-turns 1 --model haiku` once with network access and check again; the refreshed switch holds for about two minutes. In `tasks.md` a gate is the first backticked text after `Gate:`, and `deliver-check`, `ship-change` and `pr-verifier` run each `&&` part of it on its own: name the binary by absolute path inside the command (prose or an `export PATH` outside the backticks does not count) and put the `plugin test` part first, before the guard suite."

### `scripts/check.py`, `plugins/openspec/hooks/guard.test.mjs` (tooling)
`check_language()` blanks fenced blocks and backticked spans before scanning, as `check_links()` already does, keeping line numbers: a UI string quoted in backticks is a quotation, prose outside them is still refused. One `lint(...)` test beside the install-scope tests in `guard.test.mjs`: a line carrying one of the eight pt-BR markers inside backticks exits 0; the same marker outside backticks exits 1 with `docs/x.md:1: non-English text`.
- before: `for i, line in enumerate(f.read_text(encoding="utf-8").splitlines(), 1): if pattern.search(line): problems.append(...)` over the raw text of every `*.md`
+ after: `text = re.sub(r"```.*?```", lambda m: "\n" * m.group(0).count("\n"), f.read_text(encoding="utf-8"), flags=re.S)`, then `text = re.sub(r"`[^`\n]*`", "", text)`, then the same per-line scan over `text`; and the lint test above
- Answer: approved
- Applied: yes

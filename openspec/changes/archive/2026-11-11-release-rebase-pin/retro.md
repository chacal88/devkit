## Retro: release-rebase-pin

1. Went wrong: the code shipped cleanly. Two phases, two green gates (587/587, then 588/588), two review rounds and eight criteria proved; PR #21 merged as b39daf5. The cost was in the conduct around it, the first live `/conduct <id>` on a `devkit` change in the desktop app. (a) Readiness took three rounds. Round 1 found the plan's real-file smoke test contradicting the marker wording the docs task allowed. Round 3 was needed because the conducting session, before asking plan approval, found gate 2.9's bare `claude plugin validate .` already red on main: the npm Claude Code 2.1.227 rejects devkit-panel's `userConfig.language.options`, and only the app's bundled 2.1.317 passes. Readiness reads gate lines but runs none, so it could not have caught this. `CONTRIBUTING.md` step 4 still says the bare command and "about 6 minutes" for a suite that now takes about 9. `proposal.md`'s exit criteria also kept the bare command, a readiness Low that was never aligned. (b) The app refused a child-session start twice. The first time, plan approval was asked in a turn opened by the readiness agent's notification, because planning and readiness run in the background. The second time, the phase 1 gate ran as a background Bash; its end is a task notification, not a `<side-sessions-event>`, so the chain broke before phase 2. Each refusal cost the owner one more typed `/conduct release-rebase-pin`. The third run then asked the unfinished-work question about the run's own phase 1 output, which is never committed before the last phase. (c) The Group step could not work: the app nests a linked child under the conducting session and refuses to move it alone, so the `release-rebase-pin` group stayed empty. The skill's refused-call rule kept this from being a stop. (d) The devkit-panel pane cannot draw a single-change conduct, because it draws only the round's rows and the root checkout's `openspec/changes/`. The owner found it hard to read: no cards like the old orchestrator, buttons with no visible effect, sessions without icons. (e) In review round 1 every verdict was `approved`, but test-coverage carried an undisposed `[important]` (no multi-stop test). `deliver-check` mapped that to `review`, a re-review that cannot close it, instead of `fix-review`. The conducting session followed review-change's consensus rule (fix in af4055a, round 2). (f) `commit-and-pr` ignored the caller's Co-Authored-By trailer on 127097d: the caller asked for Opus 5.5 and it wrote Sonnet 5.5. The squash commit b39daf5 carries both trailers. Smaller: each child ended a first turn without an `Outcome:` line while its implementer ran in the background. Archiving a child moved the conducting session's working directory back to the main checkout. The roadmap line said "deliver-check's classification" while the classification lives in `conduct-check.mjs#releaseConflict`; the grill caught that.
2. Better next time: before asking plan approval, run the short parts of every gate on the base, since readiness runs none, and name the bundled binary wherever a gate validates the repository (proposals 1 and 4). Say in the troubleshooting table which routine turns break the start chain and what the next typed run will ask (proposals 2 and 3). Treat the conduct skill's gate-in-background, approval-from-an-automated-turn and Group step as one change of its own, so a `devkit` change goes from approval to its last phase on one typed `/conduct`. Map an undisposed important finding to `fix-review`. Build the panel's single-change view and new layout as the owner's own changes.
3. Remember: a step whose result should start a session must end in a turn the app accepts. A background Bash or agent ends in a task notification, which breaks the chain.

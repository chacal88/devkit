# Requirements

## Request

(translated from Portuguese) Roadmap round 9, line `review-workflow`: the reviewer round of ship-change and of /conduct becomes a script of the Workflow tool: the three reviewers in parallel, adversarial verification of their findings, consolidation of review.md; without changing the delivery contract.

Classification: domain=process type=feature flags=[architecture, contract] (confirmed). The contract kept is the delivery contract of `deliver-check` (its eight items) and the format of `reviews/<reviewer>.md` and `review.md`; the next step `deliver-check` suggests for one case changes (see AC-6).

## Assumptions

- ADR 0001 (`docs/adr/0001-coordination-without-a-harness.md`) says devkit coordinates "never through a harness" and runs each step as a subagent of the session the owner typed in. Running the reviewer round as a Workflow script is recorded as an exception in a new ADR, `docs/adr/0008-reviews-as-a-workflow.md` (the name is the planner's to confirm): one step only, inside the session, no state outside the repository and GitHub, the gates unchanged. ADR 0001's Note and the ADR list in `openspec/config.yaml` (`context:`, line `ADRs:`) point to it. (Owner: "ADR nova de exceção".)
- The bench is the one `review-change` already selects: the matrix in `plugins/core/skills/review-change/SKILL.md` (step 3), or the scoped list a caller passes (`next.reviewers` of `deliver-check`); every selected reviewer runs in parallel. In this repository that is at least `code-quality-reviewer`, `test-coverage-reviewer` and `adr-reviewer`. The "three reviewers" of the request means this bench, not a fixed set. (Owner: "A matriz, todos em paralelo".)
- Each reviewer runs as its own agent type (`devkit-core:<reviewer>`, the Workflow `agentType` option), so the guard's one-writer rule (`plugins/openspec/hooks/guard.mjs`, `classify` and `writeViolation`) keeps accepting `reviews/<reviewer>.md` only from that reviewer.
- Adversarial verification comes before the verdict file (owner: "Antes do arquivo"): each reviewer returns its findings to the script; every `[blocking]` and `[important]` finding gets 3 independent verifiers prompted to refute it; it is refuted when at least 2 of them refute it with evidence. `nit` and `praise` are not verified. Then the same reviewer agent type writes its `reviews/<reviewer>.md`: surviving findings stay open with their severity, refuted ones are listed with ` · refuted: <evidence>` (the disposition form `review-change` and `deliver-check` already use), and the verdict line is `approved` only when no `[blocking]` or `[important]` finding stays open. Verifiers write no file.
- The review round rules of `review-change` do not change: round counting, round 2 re-summons only the reviewers that failed, a stale-only re-review is round 1, no third round, a finding that contradicts an ADR goes to the owner.
- Without the Workflow tool (the host does not offer it, or the turn is one the owner did not type, so the tool's opt-in does not hold: an Auto-fix wake, a `<side-sessions-event>` continuation, a background task notification), the session runs the same three stages with the Agent tool (reviewers in parallel, the verifiers, the reviewer writes its file). The files have the same shape either way, and `review.md` names the path that ran (`workflow` or `agents`). (Owner: "Mesmas etapas sem Workflow".)
- `review.md` keeps being written by the session (the coordinating skill), never by a reviewer, and the gate keeps not reading it.
- The callers keep calling `review-change`: the `review` row of `plugins/openspec/skills/ship-change/SKILL.md` and the delivery `review` row of `plugins/openspec/skills/conduct/SKILL.md` change only where they describe the round.
- `deliver-check` (`plugins/openspec/hooks/deliver-check.mjs`): an approved verdict whose `[important]` (or `[blocking]`) finding has no disposition gives `next.step: "fix-review"` with that finding in `next.findings`, no longer `review` (today through the `toReview` list near line 1001). The eight items of the delivery contract and their met/open rules do not change. (Owner: "Entra".)
- Where the script lives (inline in the skill, or a file in the pack passed as `scriptPath`) is the planner's decision: AMBIGUOUS: (a) the script text inside `plugins/core/skills/review-change/SKILL.md` | (b) a file under `plugins/core/skills/review-change/` the skill passes by path; the planner resolves it against what the Workflow tool accepts from a plugin.
- Version bumps follow CONTRIBUTING: devkit-core (review-change) and devkit-openspec (deliver-check and skill text) in `plugin.json` and `.claude-plugin/marketplace.json`, with a CHANGELOG line; the CI pin in `docs/openspec-flow.md` follows the devkit-openspec version.
- This change ships with the review round it replaces (the new path is installed only after its release); its own reviews run the current way. The first live use of the Workflow path is a dogfood item of the next change, recorded in this change's retro.

## Acceptance criteria

- AC-1: `review-change` starts every reviewer of the bench (the matrix's, or a scoped list) in parallel, each as its own `devkit-core:<reviewer>` agent type, on both paths. Under the test harness with recording stubs, the Workflow script `review-round.workflow.js` makes every reviewer's `agent()` call, with `agentType: 'devkit-core:<reviewer>'`, before any of them returns; the skill's `agents` path sends one `Agent` call per reviewer (`subagent_type: devkit-core:<reviewer>`) in one message. The skill takes the `workflow` path only on a turn the owner typed with the tool offered, and runs the whole round on the `agents` path when the Workflow call is refused or errors, when its result is missing or not the shape the script returns, or when its completion notice never comes (the round is lost). A live Workflow run is not part of this criterion: it is the dogfood of the next change.
- AC-2: In the script under the harness and in the CLI's `verify` / `outcomes` chain, every `[blocking]` and `[important]` finding a reviewer returns without a disposition gets exactly 3 `devkit-core:finding-verifier` jobs, each prompted to refute it and shown no other finding, vote or verdict; it is refuted when at least 2 of the 3 refute it with non-empty evidence; `nit` and `praise` findings, and findings already marked `fixed in` or `refuted:`, get no verifier.
- AC-3: Stage 3 hands each `reviews/<reviewer>.md` to that reviewer's own agent type: the harness records `agentType: 'devkit-core:<reviewer>'` on every writer call, and the `agents` path uses the same `subagent_type`. The writer's prompt holds the `Commit: <sha>` line and every finding line verbatim (survivors open with their severity, refuted ones with ` · refuted: <evidence>`) and suggests no verdict; the round's outcome is `approved` only when no `[blocking]` or `[important]` finding stays open. `check-file` accepts a file only when line 1 is `Verdict: <that outcome>`, line 2 is the commit line and every blocking/important line is present, and exits 2 otherwise; the session never writes a verdict file. That the guard accepts a write by a Workflow agent is checked in the dogfood of the next change.
- AC-4: `review.md` consolidates the round: each reviewer's verdict, how many findings were verified and how many refuted, the consensus, the round number, and the path that ran (`workflow` or `agents`).
- AC-5: Where the Workflow tool is unavailable or not opted in (an automated turn), the session runs the same stages with the Agent tool, and the files meet AC-3 and AC-4 with path `agents`.
- AC-6: `deliver-check` gives `next.step: "fix-review"`, with the finding in `next.findings`, for an approved verdict that has an undisposed `[important]` or `[blocking]` finding (a test pins it), and the existing delivery-contract tests stay green.
- AC-7: `docs/adr/0008-*.md` records the exception to ADR 0001 (scope: the reviewer round only, inside the session, no state outside the repository and GitHub, gates unchanged), ADR 0001's Note points to it, and `openspec/config.yaml` lists it.
- AC-8: The `review-change`, `ship-change` and `conduct` skills and `docs/openspec-flow.md` describe the new round and its fallback; devkit-core and devkit-openspec are bumped with a CHANGELOG entry and the CI pin follows; `node --test plugins/openspec/hooks/guard.test.mjs` and `python3 scripts/check.py` are green.

## Out of scope

- The delivery contract itself (the eight items), the `reviews/<reviewer>.md` first-two-lines format, and the guard's writer rules.
- The review matrix (which reviewers a diff calls for), new reviewer types, and the reviewers' own prompts beyond returning findings to the script and writing dispositions.
- The conduct skill followups of the release-rebase-pin retro (gate in the foreground, approval wording, the unfinished-work question, the Group step), the panel (`panel-conduct-view`), and the commit-and-pr trailer (round 5).
- Using the Workflow tool for any step other than the reviewer round.

## Questions asked

1. [project rules] ADR 0001 says "never through a harness"; a Workflow script orchestrates agents inside the session. How do we treat it? → A new ADR of exception (0008), with a note in ADR 0001.
2. [scope] "The three reviewers": the matrix picks 2 to 6. Which bench? → The matrix (or the scoped list), all in parallel.
3. [end effect] Where does the adversarial verification land, given the one-writer rule and the checker counting undisposed findings? → Before the file: 3 verifiers per blocking/important finding, majority refutes; the reviewer then writes its file with surviving findings open and refuted ones with `· refuted:`.
4. [edges] Without the Workflow tool (automated turns, a host without it)? → The same stages with the Agent tool; `review.md` names the path.
5. [scope] The checker's `review` instead of `fix-review` for an undisposed important finding on an approved verdict? → In this change.

## Escalations

- None. ADR 0001's exception is the owner's decision (question 1) and becomes ADR 0008 for review in the plan.

AC rewording after readiness round 1 (to be confirmed by the owner at plan approval): AC-1 "runs as one Workflow script on a typed, opted-in turn, reviewers in parallel as their own agent types" → "reviewers start in parallel as their own agent types on both paths, proven by the harness and the `agents` path; the skill falls back to `agents` on a refused call, an unreadable result or a lost notice; the live run is the next change's dogfood"; AC-2 "every blocking/important finding is checked by 3 verifiers, 2 refute" → "the same rule, proven in the script under the harness and in the CLI chain, with already-disposed findings not verified again"; AC-3 "each file is written by that reviewer's agent type (the guard accepts it)" → "each writer call carries that reviewer's agent type with the lines and no verdict, and `check-file` accepts only the right file; the guard accepting a Workflow agent's write is the next change's dogfood".

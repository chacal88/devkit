## Retro: review-workflow

1. Went wrong: the code shipped cleanly. Two phases, two green gates (637/637 at 1.5, 648/648 at 2.8), two review rounds and eight criteria proved; PR #23 merged as cd37b1f with `check` and `devkit-reviews` green. Two lessons of the last retro paid off. The gate parts ran on the base before plan approval, so readiness needed no round for a red gate. The troubleshooting row predicted the first refused start. The cost was elsewhere again. (a) Readiness round 1 was NEEDS-REVISION with three blockers, and all three came from Workflow-tool facts the repository cannot verify: there was no fallback for a call that is accepted but returns a bad result or no notice; AC-1 to AC-3 could only be shown by a live run; and task 1.2 left the result convention to the implementer. AC-1 to AC-3 were reworded to what the harness and the `agents` path prove, with the live half moved to the next change's dogfood (the line at the end of `requirements.md`), and the owner confirmed it at plan approval. The grill had already settled the scope, the bench, where verification lands and the fallback. It never asked what this change can prove and what only a live run can, so readiness asked it. (b) Child sessions needed a typed `/conduct` for every phase. Phase 1's start was refused because plan approval was asked in a turn the readiness agent's notification opened, as the row added by release-rebase-pin says. The phase 1 gate then ran in the foreground of the `<side-sessions-event>` turn, the fix that retro proposed, and the chain held. Phase 2's start was still refused, with a new error: in a continuation turn the app starts a session only "where this one runs". The conducting session runs in the main checkout and the child's `cwd` is the change worktree, so a continuation turn cannot start any phase. Each refusal cost a typed run plus an unfinished-work answer. (c) The Group step was refused again: the child stayed nested under the conducting session. (d) Review round 1 ran on the installed agents path, with five reviewers. It failed on two `[important]` findings on approved verdicts. First, the workflow path never compared the writer's returned verdict and commit with the computed outcome (test-coverage). Second, the verifier count and the majority lived outside the rules section, in both the script and the CLI (architecture). Both were fixed test-first in 01ee296, and round 2 passed. The installed deliver-check (devkit-openspec 0.10.3) mapped those undisposed findings to `review`, which is the exact behaviour this change fixes to `fix-review`. The conducting session followed review-change's consensus rule instead. (e) Eight nits were left open (row 7). One of them can loop: after round 2, an approved verdict with an undisposed finding can cycle `fix-review`/`review`, because the deadlock stop counts only rejected reviewers. On the good side: every commit carried the caller's Opus 5.5 trailer, because the prompt said "the caller's trailer wins; owner's choice" (contrast 127097d in release-rebase-pin).
2. Better next time: when a change is built on a harness tool, the grill asks one question up front: which criteria can this change prove (tests, the fallback path), and which are the next change's dogfood? Then readiness does not discover it (proposal 2). State in the troubleshooting row that a continuation turn cannot start a child whose `cwd` is not where the conducting session runs, so the owner knows each phase needs a typed run (proposal 1). Give `commit-and-pr` the trailer as the owner's choice until the round 5 fix lands (proposal 3). Fold the session-start `cwd` refusal into the conduct skill change that the release-rebase-pin retro asked for. List core's test in CONTRIBUTING's suite sentence (proposal 4).
3. Remember: when a change rests on a harness tool, decide in the grill what its tests prove and what is the next change's dogfood.

The refused-start row names the third refusal. A continuation turn that keeps the chain still cannot start a child whose `cwd` (the change worktree) is not where the conducting session runs. So in this app version every phase starts on a typed run.
- before: | A start was refused: `waiting for the owner: start session <id> phase <n>` | The app accepts a start only on your typed turn and its unbroken chain of continuation turns; an automated turn broke the chain. Two such turns are routine in a `devkit` change: plan approval asked in a turn that a background agent's result opened (planning and readiness run in the background), and a phase gate run as a background Bash, whose end is a task notification, not a `<side-sessions-event>` | Type `/conduct <id>` (or `/conduct round <n>`) again; the phase is never run as a subagent in its place. That run asks about unfinished work when earlier phases are done, because no phase is committed before the last one: answer that it should go on |
+ after: | A start was refused: `waiting for the owner: start session <id> phase <n>` | The app accepts a start only on your typed turn and its unbroken chain of continuation turns; an automated turn broke the chain. Two such turns are routine in a `devkit` change: plan approval asked in a turn that a background agent's result opened (planning and readiness run in the background), and a phase gate run as a background Bash, whose end is a task notification, not a `<side-sessions-event>`. A continuation turn that keeps the chain (a gate run in the foreground of the `<side-sessions-event>` turn) is still refused when the child's `cwd` is not where the conducting session runs: the app answers that it "can only start sessions where this one runs".

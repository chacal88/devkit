### The change against ADR 0007 (new on main)

ADR 0007 decides which changes a run of the conducting skill conducts; the panel conducts nothing, so its Decision binds the skill and not the pack. Checked anyway, line by line, that the panel neither contradicts it nor pulls its review trigger:

- **§ Decision 1 (`/conduct <id>` conducts the named change).** The `Conduct` button fills `/conduct <id>` when the probe answered `yes` (`plugins/panel/hooks/commands.ts:38`, `i18n.ts:49`, `:82`); the probe (`register.tsx:72-76`, design D8) runs `conduct-check --json --change <id>` once per session and reads `yes` on exit 0, which main's checker now gives (`plugins/openspec/hooks/conduct-check.mjs:466-475`, `:619` single-change mode). The text goes into the prompt box through `$.prompt.fill` (`register.tsx:185-188`); the owner presses Enter, so the run that follows is the owner's typed turn the ADR requires. The sibling landing first is exactly the case design.md's Risks foresaw (`design.md:397-398`): the button switched with no code change.
- **§ Decision 2 (the sweep only on an explicit `round <n>`; a bare `/conduct` lists and asks, never sweeps).** The panel runs a bare `conduct-check --json` in the root (`register.tsx:50-58`) to draw the round. That is a read of the round report, not a conduct: the panel acts on nothing in it (design D16, AC-3, AC-8). The conduct skill's own rule "a bare `conduct-check` is never run: it would sweep the round" (`plugins/openspec/skills/conduct/SKILL.md:21`, `:156`) binds the skill's runs, which act on the report; ADR 0007 § Consequences says the one engine "serves both modes and any later panel", which is this reading. A `create` or `new-change` row fills a bare `/conduct` (`commands.ts:37`), which under § Decision 2 lists the open ids and asks: safe, see the nit below on the wording.
- **§ Decision 3 (unfinished work in a worktree is reported before the change runs).** The panel runs `deliver-check <id> --json` in the row's worktree (`register.tsx:61-68`), a read, and runs nothing of the change; the report and the question stay with the skill on the owner's turn.
- **§ Decision 4 (ADR 0006's session rules hold per change).** The panel starts, groups, archives and messages no session; it reads the app's list once per refresh behind `mayList` (`register.tsx:81-97`, `sessions.ts`), which ADR 0006 § Decision 4 counts as state a coordinator may read.
- **Review trigger: "a caller other than the skill (a panel) needs the checker to list candidate changes".** Not pulled: the other open changes and the archived ones come from `$.fs.list` of `openspec/changes/` and `openspec/changes/archive/` (`plugins/panel/hooks/project.ts:92-104`, design D5 "Both from `$.fs.list`, no checker", AC-3), and the change edits nothing under `plugins/openspec/hooks/` (the diff stat touches only `project-settings.mjs` there). The checker lists nothing for the panel that it did not list for the skill.

### Findings
- [important] plugins/openspec/hooks/release-rebase.mjs:258 — The post-rebase `try` only turns `ReleaseError` into the documented exit 2 with a restore. Any other exception is rethrown: `JSON.parse` in `resolveManifest` (called at :232) or in `resolveVersions` on a malformed manifest on the base or the change, or a write error. Then the branch stays rebased, part of the files are already written, and the process dies with a stack trace and exit 1. The header (:6) promises 0, 2 or 3, and "not resolvable: the branch is back at its old head". A hand-edited broken `plugin.json` is a plausible input. · fix: catch every error there, call `unresolved({ conflicts: [], error: e.message })`, and rethrow nothing. Add a test with an invalid JSON manifest on the base.
- [nit] plugins/openspec/hooks/conduct-check.mjs:489 — `selectDispatch(changes, busy)` gets the raw `--busy` list, but `busy` in the summary is filtered to known ids (:487-488). A stale id lowers the cap. I ran `selectDispatch` with 3 runnable changes and busy `['zzz']`, and it returned `['a','b']`. This is safe (it under-dispatches) but inconsistent with the reported `busy`. · fix: pass `busyIds` to `selectDispatch`.
- [nit] plugins/openspec/hooks/deliver-check.mjs (`started` exemption, ~:973) — Ticking one task skips the plan-approval check. The design records this on purpose (design.md:186, so in-flight changes keep running). So it is not a false claim. But `approval.md` is a soft gate: the guard stops other agents from writing it, not the main session from ticking a box first. Worth one line in the ship-change "Never" list.
- [praise] plugins/openspec/hooks/release-rebase.mjs:140-210 — Safe by construction: it never pushes or commits, `restore()` puts back the written files before `reset --keep`, and every unresolvable case returns to the old head. It exited 0 and left the manifests at 1.2.0, the CHANGELOG as `1.2.0 — mine` above `1.1.0 — theirs`, and the changes uncommitted. The change's own empty commit was dropped by the rebase.

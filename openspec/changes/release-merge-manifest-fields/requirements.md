# Requirements

## Request

> release-merge-manifest-fields: `release-merge.mjs --merge` refuses a head whose manifest changes anything but the version ("a manifest was edited beyond its version"), so a change that edits a pack's description cannot ride a train (project-setup, pull request 148, was left for it). Renumber the version and keep the head's other manifest fields when only one side changed them, refusing only a field both sides changed, with a test of each case.

## Classification

domain=process type=feature flags=[contract] (strict-assumed; the release step's refusal is a documented rule other steps rely on)

## Assumptions

<!-- Each confirmed by the owner. Literal paths, fields, names. -->
- The rule lives in the version step both modes share: `resolveVersions` and the manifest rewrite in `main` of `plugins/openspec/hooks/release-merge.mjs` (the refusal built at `release-merge.mjs:713`). `--merge` (a head with no release note joining a train) and `--base` (origin/<base> merged into a change branch) both use it, with the change side and the base side swapped (`release-merge.mjs:684`, `:712`).
- A "manifest" is one of the files the step already rewrites: `plugins/*/.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` (`MANIFEST`, `RELEASE_FILE`).
- A "field" is a JSON leaf path as `diffPaths` already computes it after `withoutVersions`: object keys walked one by one, `plugins[]` entries matched by `name` (for example `plugins[devkit-compozy].description`, `description`, `keywords`); an added or removed key is a field.
- The change side edited a field when its value differs between the merge base and the change side; the base side edited it when its value differs between the merge base and the base side.
- The written manifest is the base side's text with the renumbered versions (as today, `resolveManifest`), plus the change side's value of every field only the change side edited. A field only the base side edited keeps the base side's value.
- `docs/catalog.md` is still regenerated by `scripts/gen-catalog.py` whenever a manifest is rewritten (`release-merge.mjs:734-740`), so a kept description reaches the catalog with no new step.
- The noted path (`numberRelease` / `assignBlocking`, `release-merge.mjs:338-380`) is unchanged.

## Acceptance criteria

<!-- Stable ids, observable and testable. -->
- AC-1 `head-only-field-kept`: `release-merge.mjs --merge <head>` where the head bumped a pack's version and edited its `plugin.json` `description` (and the matching `marketplace.json` entry), and the train did not edit those fields, exits 0 with `resolved: true`; the committed manifests carry the version renumbered above the train's and the head's description.
- AC-2 `train-only-field-kept`: when only the train edited a manifest field beyond its version (the head bumped only the version), the join exits 0 and the committed manifest keeps the train's value of that field with the renumbered version.
- AC-3 `both-sides-field-refused`: when the head and the train both edited the same manifest field, the join exits 2 with `resolved: false`, the branch is at its old head with no merge in progress and a clean tree, and `error` starts with `a manifest field was edited on both sides:` and names the file and the field path.
- AC-4 `disjoint-fields-merged`: when the head edited one field and the train edited another field of the same manifest, the join exits 0 and the committed manifest holds both edits and the renumbered version.
- AC-5 `base-mode-same-rule`: `release-merge.mjs --base <base>` on a change branch that edited a pack's description, with the base not editing it, exits 0 and keeps the branch's description with the version renumbered above the base's; a field both sides edited exits 2 as in AC-3.
- AC-6 `catalog-follows`: after AC-1's join, `python3 scripts/gen-catalog.py --check` passes on the committed tree (the catalog is regenerated from the kept description).
- AC-7 `docs-say-the-rule`: `docs/openspec-flow.md` ("Classification", "The version rule"), `CONTRIBUTING.md` (the train-join line) and the `change-coordination` spec state the new rule (fields only one side edited are kept, a field both sides edited aborts) and no longer say a description edit aborts or that such a change is delivered alone.

## Out of scope

- The noted path (`numberRelease`, `assignBlocking`) and its handling of a conflicting manifest.
- Accepting a field both sides edited to the same value.
- A new or removed pack entry in `marketplace.json` `plugins[]`, or a new pack's manifest.

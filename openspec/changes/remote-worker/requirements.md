# Requirements

## Request

> a change can run on another machine: the project configures a command that starts a change there and one that asks its state, and the roadmap coordinator chooses where each change runs. Required by the owner on 2026-11-21: no machine opens a change that is already open on another one. That day three changes were opened on a second machine (a Linux worker reached over SSH), each in a session of its own; their folders and branches lived only there, so `/devkit status` on the Mac listed them as ready and waiting for a place, and a `/devkit roadmap` run on the Mac would have opened them again. Before it opens a change, the roadmap coordinator learns from every machine (or from what they share, such as a pushed branch or a claim on GitHub) which changes are open and where, and `/devkit status` shows each open change with its machine. Candidate to weigh in its grill, recorded by the owner on 2026-11-21 after the first real `/devkit roadmap` run: Claude Managed Agents (beta, Claude API), where a session runs on Anthropic's machines in a container of its own, so the owner's processor load no longer holds a start; its multiagent orchestration gives one session a coordinator agent that delegates to other agents, each in a thread of its own (an isolated, persistent event stream with its own model, prompt and tools, all sharing the session's container), which maps to a change per session and a stage per thread (at most 25 child threads per session); and its workflow runs let the agent write a program that runs many agents in phases in the background and combines what they return, which maps to the review round (reviewers, then the verifiers of their findings). Pages the owner pointed to: `managed-agents/overview`, `managed-agents/session-threads`, `managed-agents/multiagent-orchestration` and `managed-agents/workflow-runs` under `platform.claude.com/docs`. Open points: the sessions show in the platform Console, not in the app's sidebar; the owner's answers and approvals reach a session only as messages sent through the API; each container needs the repository, a GitHub credential in a vault and the devkit packs; session runtime is billed on top of tokens Carried from the managed-agents-study: its items F-3 and X-5 and its open points O-1 to O-7 are the grill's input. A Managed Agents session runs none of devkit's hooks, so a stage run there is held only by the pull request's checks (ADR 0010, decision 5); a cloud sandbox takes the processor load off the owner's machine and a self-hosted sandbox does not; running only stages remotely keeps the coordinator in the owner's session, while moving the coordinator itself means the change writes the ADR that amends ADR 0011 (and ADR 0013 for the roadmap).

## Assumptions

<!-- Each confirmed by the owner. Literal paths, fields, names. -->
- Opening a change (`plugins/openspec/hooks/change-loop.mjs` `open`, which the roadmap coordinator also calls) first asks GitHub whether `refs/heads/<id>` exists on `origin` and refuses the open when it does, naming the machine that holds it; otherwise it commits the change folder with `requirements.md` and the machine's name and pushes the new branch, a push that only creates the ref, so the second of two simultaneous opens is refused by GitHub. A project with no GitHub `origin` opens as today, with no claim.
- The machine's name lives in the change folder as one field of a file the planner names (`AMBIGUOUS: (a) a key in openspec/changes/<id>/.openspec.yaml, if the openspec CLI accepts an extra key | (b) a file of its own such as openspec/changes/<id>/machine; the planner resolves`). It is the app SSH connection name from `machines` when the change runs on a listed machine, else this machine's hostname.
- The `machines` setting is a new user setting of the devkit-openspec pack (`plugins/openspec/.claude-plugin/plugin.json`, `userConfig.machines`, beside `userConfig.load_limit`); each entry gives `host` (the app SSH connection name, as `list_start_targets` lists it), `folder` (the repository folder on that machine) and `places` (a whole number). This machine is the first entry or implicit; its exact encoding (the setting is a string today, like `load_limit`) is the planner's.
- A place is taken by a change from its implementation on (code, review, delivery), not by its grill or plan; the default number of places of this machine is the planner's, kept compatible with today's `/devkit roadmap <n>` and `load_limit`.
- A change is assigned to its machine at open and stays there to its archive.
- The coordinating session starts a remote change session with the host's session-start tool (`target: "ssh"`, `host: <machines[].host>`, `cwd`: the change's worktree on that machine), only on a turn the owner typed, as ADR 0014 decision 2 says for local sessions; the change's worktree on the remote machine is opened there before the session starts (how: over SSH or by the started session itself, the planner's).
- The state of a remote machine is asked over SSH with that machine's `/devkit status` in a machine-readable form; a machine that does not answer within a bounded time is "no answer".
- This run is live input: the Mac's coordinating session started this session on the SSH connection `avel` and reached it by message; the Mac's `/devkit status` listed the Linux changes as ready because their branches lived only on the Linux worker.

## Acceptance criteria

<!-- Stable ids, observable and testable. -->
- AC-1 `open-refuses-claimed` — Opening a change whose branch already exists on the GitHub `origin` is refused with a reply naming the change and the machine that holds it, and creates no worktree, no folder and no local branch.
- AC-2 `open-pushes-claim` — Opening a change in a project with a GitHub `origin` leaves `refs/heads/<id>` on `origin` holding the change folder with `requirements.md` and the machine's name, with or without `machines` set.
- AC-3 `open-race-one-wins` — Of two opens of the same id racing from two checkouts against one remote, exactly one ends with a claim; the other is refused and leaves no worktree or local branch.
- AC-4 `no-origin-unchanged` — In a project with no GitHub `origin`, opening a change behaves as today: no push, no refusal.
- AC-5 `status-shows-machine` — `/devkit status` lists every open change of the roadmap, those open only on another machine included, each with its machine, and never lists a change claimed on GitHub as ready.
- AC-6 `roadmap-never-reopens` — A `/devkit roadmap` run never opens a change whose branch exists on `origin`, whichever machine claimed it.
- AC-7 `machines-setting` — With `machines` unset, `/devkit roadmap` places every change on this machine exactly as today; with it set, the run reads each entry's connection name, folder and places, and refuses an entry that lacks one of them with a reply naming the entry.
- AC-8 `open-on-fewest` — At open, the roadmap coordinator puts a change on the reachable machine with the fewest open changes, ties broken by the configured order; this machine is skipped while its processor load is above `load_limit`.
- AC-9 `remote-session-start` — A change placed on a remote machine gets a session started by the coordinating session through the app's SSH target in that change's worktree there, nested under the coordinating session, only on a turn the owner typed.
- AC-10 `place-at-implementation` — A change's grill and plan never wait for a place; after its plan is approved, the change script refuses to start the implementation while its machine has no free place, ending the turn in ⏳ with a line that says it waits for a place, and implements once a place is free.
- AC-11 `wake-on-free-place` — When a place frees on a machine, the coordinating session sends a message to a change of that machine waiting in ⏳, and that change then implements only if the change script finds the place free.
- AC-12 `unreachable-machine` — A machine that does not answer over SSH gets no new change; the board marks it "no answer"; `/devkit status` shows each of its open changes with the machine and "no answer" in place of the stage; its changes keep their places and nothing reopens them elsewhere.

## Out of scope

- Claude Managed Agents as a place where a change or a stage runs: it becomes a roadmap line of its own (grill answer 1).
- Moving an open change from one machine to another (answers 5 and 7).
- Starting a change on another machine without the desktop app (a shell command such as `ssh <host> 'claude -p ...'`, answer 3).
- Cloud sessions of the app as a machine.

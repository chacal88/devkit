# Requirements

## Request

> Asked by the owner on 2026-11-24, after the first two delivery trains: "Precisamos resolver essa questão de versão. Sempre vai dar conflito." A change stops choosing numbers. Today every change writes its release into files every other change also edits (the packs' plugin.json, .claude-plugin/marketplace.json, CHANGELOG.md, the CI pin lines of docs/openspec-flow.md, the pin assertion in a test) and picks the next free ADR number, so any two changes conflict on those lines by design: the train renumbers the release files when it joins heads, but it left every boarded change of train 2 for the pin assertion in plugins/openspec/hooks/change-loop-compozy.test.mjs, and ADR numbers picked in parallel collided four times in one day, each renumbering staling reviews and sometimes the owner's plan approval. Wanted: each change carries a small release note in a file of its own (which pack changes, how big the bump is, the changelog line) and names its ADR without a final number; the delivery (the train, and the single-change merge step where there is no train) assigns the version and the ADR number once, at the moment it reaches the default branch, writes the manifests, the changelog, the pin and the tag, and no change branch edits a shared release line. In the grill: what a change's branch shows before it merges (how its ADR and release are named), what happens to a consumer project with no train and to one with no release file, how the archive check and the release tag follow, and how changes already open move over.

## Assumptions

Classification: domain=process, type=feature, flags=[architecture, contract] (confirmed: the `devkit` script was chosen for it).

The grill's questions 1 to 4 were answered by the coordinating session under the owner's delegation of 2026-11-24 ("responda o maximo possivel"); the owner can overturn each one at the plan approval, and the plan summary lists them first.

- Decision 1, taken by the coordinator under delegation: with no train the numbers are written on the change's own branch, by one delivery step (`assign-release`) that runs last, before `enable-auto-merge`, and runs again after every merge of the base; with a train they are written by the join (`node plugins/openspec/hooks/release-merge.mjs --merge <rev>`). No other step, and no change author, writes a release line. Reasons: the owner has three consumer projects and wants one behaviour with or without a train; a release pull request after the merge costs one more pull request and one more wait per change; the step writes only release-class files, which ADR 0025 already keeps from staling evidence and reviews.
- Decision 2, taken by the coordinator: the release note is a plain file `openspec/changes/<id>/release.md`, not a stage and not a new flow version. Reasons: a new flow version leaves open changes on two flows and has, each time, left the installed plugin unable to read `main`'s `flow.json`. Fact: a file outside a stage is not in what the plan approval covers (`plugins/openspec/hooks/flow-check.mjs`, the `stage.staleAfter` loop reads `facts.files[<stage>]`, and `approval.md` records the readiness verdict's hash), so `deliver-check` compares the hash of `release.md` at the head with the hash recorded in `approval.md` (a `- Release note: sha256:<hash>` line written with the approval) and refuses a change whose note differs. (Corrected while planning: the first wording compared with the commit named in `approval.md`'s header, but that commit holds no plan file.)
- Decision 3, taken by the coordinator: a change names its ADR `docs/adr/<slug>.md` (no number) and cites it as `ADR [<slug>]`; the same step that gives the version gives the number, renaming the file to `docs/adr/<NNNN>-<slug>.md` with the next free number on the base and rewriting every citation outside the change's own folder. The change's own folder keeps the citation as written, so no plan file, approval, review or evidence changes. The ADR's own `Change:` line resolves the citation after the merge. The renamed ADR and the rewritten citations are treated as release files are by ADR 0025 (not own files; the train check allows them).
- Decision 4, taken by the coordinator: any project that names `devkit.release_tag` gets the same behaviour. The delivery writes the top-level `version` of the file that key names and, only when the project already has `CHANGELOG.md` at its root, the note's changelog line there; it creates no file a project does not have and reads no layout it cannot find. This repository's layout (the `plugins/*/.claude-plugin/plugin.json` of each pack, `.claude-plugin/marketplace.json` with `metadata.version`, `CHANGELOG.md`, `docs/catalog.md` through `scripts/gen-catalog.py`, the CI pin lines of `docs/openspec-flow.md`) stays a second set of rules, active when those files exist. A project with no `devkit.release_tag` sees nothing new. The kind of bump comes from the note, never guessed.
- The note's form: `openspec/changes/<id>/release.md` holds, in this order, a `packs:` list (a pack name and `patch`, `minor` or `major`; an empty list means no release), an optional `marketplace:` bump that defaults to the largest pack bump, an optional `release:` bump for the file `devkit.release_tag` names (consumer projects), a changelog title and a changelog body. One function reads it and refuses a malformed note with a plain message (`release-merge.mjs` or a module it imports; the plan names it).
- The slug is derived from the change id (`<change-id>` for the first ADR of a change, `<change-id>-<topic>` for more) and a second file with the same slug is refused (`docs/adr/` and `docs/decisions/`).
- Every reader of ADRs accepts the unnumbered form before the delivery and refuses it on the base branch: `scripts/check.py`, `plugins/core/agents/adr-author.md`, `plugins/core/agents/adr-reviewer.md`, the ADR list in the `context:` of `openspec/config.yaml`, `plugins/openspec/hooks/conduct-check.mjs` (`ADR_FILE`, `adrClash`, the `renumber-adr` step) and `plugins/openspec/hooks/guard.test.mjs`; the plan lists each test file that pins an ADR file name.
- A citation of an ADR of another open change (`amends ADR [<slug>]`) resolves once the cited ADR has landed; while it has not, the step refuses with a plain message.
- The delivery's state is derived, no marker commit: the release files at the head equal to the base's means `assign-release` is next; equal to what the step computes from the base plus the notes means done; anything else is refused as "release lines edited by hand". A change that touches a pack's files and has neither a note nor a bump of its own is refused as "no release".
- The release tag (ADR 0019, `deliver-check.mjs#releaseTagFacts`) is unchanged: it reads the release file's `version` at the merge commit and its first parent.
- The archive check is unchanged by this change; `archive-release-pin` (merged: ADR 0027, which amends ADR 0003, and ADR 0030) lets the CI pin lines pass unnamed in it, and makes `plugins/openspec/hooks/change-loop-compozy.test.mjs` read the version from `plugins/openspec/.claude-plugin/plugin.json`. The line between the two: that change makes a rewrite of the pin lines acceptable to the archive check and to its own test; this one removes the rewrite from every branch, so only the delivery step edits a pin line. This change does not edit that test and does not wait for it (it has merged).
- The ten changes open today follow the old rule until they merge: no note, a bump of their own, renumbered by `release-merge.mjs --base` or `--merge` as today, and `renumber-adr` for a clashing ADR number. Moving one over is adding its note and putting its release files back to the base's; it is done only when the owner asks. Removing the old rule is another change.
- This change's own release and ADR follow the old rule while it is being delivered (the mechanism does not exist yet), with the number "assigned at merge" by the train's join; its plan names no literal version or ADR number.
- The new ADR amends ADR 0022 (decision 3 and its rejected alternative "Renumber releases on each change branch"), ADR 0025 (the release-class files grow by the numbering of an ADR, and decision 3's plain-commit rule is adjusted) and builds on ADR 0003, ADR 0027 and ADR 0030 without amending them: the archive check's pin-line rule stays as a safety net for archive pull requests and changes on the old rule. A text that pins the old rule changes with it (`CONTRIBUTING.md` step 5; `openspec/config.yaml` Conventions and the `tasks` rule; `plugins/core/agents/tdd-implementer.md`, `plugins/core/agents/change-planner.md` and `plugins/core/skills/plan-readiness-review/SKILL.md` with their CompozyOS copies; `docs/openspec-flow.md`; `openspec/specs/change-coordination/spec.md`, scenario "An ADR number taken").

## Acceptance criteria

- AC-1 `release-note-file`: a change carries `openspec/changes/<id>/release.md` written with the plan; one function reads it and a malformed note is refused with a plain message naming the field (one test per field, negatives included).
- AC-2 `no-hand-edit`: a branch of a change with a note, before the numbers are assigned, holds the release files exactly as the base has them; `deliver-check` refuses a branch whose release files are neither the base's nor what the step computes, saying "release lines edited by hand".
- AC-3 `train-join-from-notes`: two boarded changes with notes that both bump the same pack, with neither branch touching a release line, join on one train with no conflict: the first boarded takes the next version, the second the one after, each CHANGELOG entry, the marketplace version, the catalog and the CI pin follow, and each change's head, evidence and reviews stay current.
- AC-4 `assign-before-auto-merge`: with no train, `assign-release` runs last, before `enable-auto-merge`, commits only release files, leaves the evidence and the reviews current, and runs again after a merge of the base that moved the release; two such changes in a row never conflict on a release line.
- AC-5 `adr-numbered-at-delivery`: a change that names its ADR `docs/adr/<slug>.md` and cites it `ADR [<slug>]` has it renamed to `docs/adr/<NNNN>-<slug>.md` (the next free number on the base) and every citation outside the change's folder rewritten, by the train's join or by `assign-release`; no file of the change's folder changes, so the readiness verdict, the plan approval, the reviews and the evidence stay current and the owner is not asked for the approval again.
- AC-6 `adr-unnumbered-readers`: before the delivery every reader of ADRs listed in the assumptions accepts `docs/adr/<slug>.md`; on the base branch `scripts/check.py` refuses an ADR with no number, and a second file with one slug is refused.
- AC-7 `adr-cross-citation`: `amends ADR [<slug>]` of another change's ADR resolves once that ADR has landed, and `assign-release` or the join refuses with a plain message naming the slug while it has not.
- AC-8 `consumer-release-file`: a project that names `devkit.release_tag` gets its file's `version` written from the note's bump, and its root `CHANGELOG.md` gets the note's line only when the file exists; no file is created and no layout is assumed.
- AC-9 `consumer-nothing-new`: a project with no `devkit.release_tag`, with no train, with no release file or with no `docs/adr` sees no new step, no new refusal and no new file; a test per case.
- AC-10 `old-rule-kept`: a change with no note and a bump of its own (opened before this change) joins a train, merges alone and renumbers on a base update exactly as before, and a clashing ADR number still takes `renumber-adr`.
- AC-11 `no-release-refused`: a change that touches the files of a pack, has no note and no bump of its own, is refused as "no release", and one with a note whose `packs:` list is empty passes.
- AC-12 `note-after-approval`: a `release.md` that differs from the one at the commit recorded in `approval.md` is refused until the plan is approved again.
- AC-13 `tag-unchanged`: the release tag of ADR 0019 is asked and pushed for the merge that carries the numbers, with the same rules (a test through the train and one through a single merge).
- AC-14 `rules-and-docs`: every text and test the assumptions list is changed with the rule, `python3 scripts/check.py`, `python3 scripts/gen-catalog.py --check` and `node plugins/compozy/skills/compozy-setup/scripts/gen-agents.mjs --check` pass, and a new ADR records the decisions and amends ADR 0022 and ADR 0025.
- AC-15 `real-run-every-case`: the real-run proof covers every case the plan declares, each input variant and the conducting session's own part: the planner writing `release.md`, the adr-author drafting `docs/adr/<slug>.md`, a train of two noted changes, a single merge with a noted change, an old-rule change, a consumer project, and each refusal (hand edit, no release, note after approval, unlanded citation, duplicate slug); not one case plus prose tests.

## Out of scope

- Moving the ten open changes over to the note, and removing the old rule (`release-merge.mjs --base` on a branch's own bump, `renumber-adr`).
- The test `plugins/openspec/hooks/change-loop-compozy.test.mjs` and the archive check's pin rule: `archive-release-pin` (PR 107).
- A new stage or a new flow version, and a release pull request after the merge.
- GitHub Releases, annotated or signed tags, and a CHANGELOG for a project that has none.
- Any consumer layout other than the file `devkit.release_tag` names and a root `CHANGELOG.md`.

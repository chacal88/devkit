# Proposal

Change: `openspec-type-flag` · Date: 2026-11-28 · Owner: Kaue (chacal88) · PRD / tech spec: n/a
(source: `requirements.md`; the how is in `design.md`). Plan base: `c055e55`.

## Why

`openspec validate <id> --strict` fails with `ambiguous_item` (exit 1) when a change and a canonical spec
have the same id. Checked at plan time with the CLI 2.0.0 in a scratch repository: the bare form failed and
`openspec validate <id> --type change --strict` answered `Change '<id>' is valid`. Eight archived change ids
of this repository equal a spec name (`change-state`, `commit-attribution`, `compozy-driver`,
`delivery-models`, `delivery-train`, `project-setup`, `release-tags`, `stage-models`; the roadmap line says
seven). `change-loop.mjs merge-check` already passes `--type change` (`plugins/openspec/hooks/change-loop.mjs:1790`).
The planner, the readiness reviewer, the openspec-validator agent, two skills and the schemas' stage gates
still tell an agent to run the bare form. So a change named after a capability fails its own plan gate and
its structural check, and nothing stops the bare form from being written again.

## What Changes

- Every place whose text tells an agent or a stage to validate one change tells it to run
  `openspec validate <id> --type change --strict`, keeping any other flag it has (`--no-interactive`). These are:
  `plugins/core/agents/plan-readiness-reviewer.md` (step 3), `plugins/core/agents/change-planner.md`
  (step 4 and the next-step line), `plugins/openspec/agents/openspec-validator.md` (check 1 and its report
  line), `plugins/core/skills/plan-readiness-review/SKILL.md` and `plugins/core/skills/review-change/SKILL.md`,
  and the seven `Gate:` lines of the `devkit` and `devkit-lite` schemas.
- The two skills drop their fallback to the bare form ("if the CLI lacks those flags", "when the CLI
  supports them"): devkit supports OpenSpec 2.x only (`docs/openspec-flow.md:131`), and 2.0.0 accepts
  `--type change`.
- The copies follow their sources. The schema copies under `openspec/schemas/` are written by
  `install-schemas.sh` and stay byte-identical. The CompozyOS agents under `plugins/compozy/kit/templates/agents/`
  are regenerated by `gen-agents.mjs`, and those under `.compozy/agents/` are reinstalled by `install-kit.mjs`.
  None is edited by hand.
- `scripts/check.py` gains a check. It fails, naming the file and the line, when an agent, skill, schema or
  CompozyOS agent file holds in code (a backtick span or a fenced block) an `openspec validate` command
  that names an id without `--type change`. A new test file holds the tests of that check, the
  text test and the real-CLI test of a change and a spec with the same id.
- Not breaking: a project on OpenSpec 2.x runs the same validation, now unambiguous.

## Non-goals

- Text that only names the command without telling anyone to run it on a change: `docs/roles.md:154`,
  `docs/coordination-design.md:181`, the agent descriptions in `plugins/openspec/README.md` and
  `docs/catalog.md` (and the `openspec-validator` frontmatter `description` they are generated from, which
  names `openspec validate --strict` with no id), and the schema sentences "`openspec validate` rejects ...".
- The `openspec validate --all --strict` snippet of `docs/openspec-flow.md` and the old-release fixtures
  under `plugins/openspec/skills/devkit/scripts/fixtures/schemas-0.13.0/`.
- Any change to how `change-loop.mjs merge-check` validates.

## Acceptance criteria

- AC-1 `every-run-passes-type`: Every file in scope tells the agent to run `openspec validate <id> --type change --strict`; no file in scope still holds the bare form or a fallback to it, and `node plugins/compozy/kit/scripts/gen-agents.mjs --check` passes.
- AC-2 `same-name-proof`: A test creates, in a scratch repository with the real `openspec` CLI, a change and a canonical spec that share one id: the bare `openspec validate <id> --strict` answers `ambiguous_item`, and `openspec validate <id> --type change --strict` validates the change.
- AC-3 `bare-form-refused`: A repository check that runs locally and in CI fails when an agent, skill or schema file tells an agent to run `openspec validate <id>` on a change without `--type change`, naming the file and the line; on the files of this change it passes.
